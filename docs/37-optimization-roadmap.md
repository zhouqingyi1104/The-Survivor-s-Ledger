# 优化路线图（2026-10-28）

承接 [10 内容路线图](10-roadmap.md)。10 记录"做了什么"；这篇回答"接下来做什么最值"，并说明为什么。

## 0. 结论

系统已经很宽：20 多个子系统、约 2.5 万行游戏代码和同量测试、7 天 151 次提交。但**到今天没有一个真人玩完过一局**——每一批的验收记录里，"真人试玩"都写着 NOT RUN，`user://reports/` 里也没有一份导出过的试玩报告。

所以下一步最值钱的不是第 21 个系统，而是两件事：

1. **让第一批玩家玩上**，拿回可复现的报告；
2. **把现有内容收拢成玩家看得懂的样子**——现在信息都在，但很多是把规则条款直接放到了屏幕上。

新内容等试玩证实核心循环成立以后再加。

## 2. 问题诊断（按对玩家的伤害排序）

### P0-1 没有真人验证，后面每一批都在猜

M3 以后的所有功能——身份专法、可变开局、轮回调查、差事单、宅院营造——都没有被玩家碰过。机器人能证明"不崩、数值单调、单子排得满"，证明不了"玩家看得懂、觉得好玩"。

**后果**：下一个功能值不值得做，现在无从判断；越往后叠，回头改的成本越高。

### P0-2 工作区里结局页是坏的

`scripts/ui/screens/ending_screen.gd` 未提交的改动在第 38 行用了已存在的变量名 `line`，解析失败。从这个工作区（比如 `启动游戏.bat`）启动的人，一旦劫满、撤离或破阵就进不了结局页。用干净提交打出来的包不受影响。这份改动是 10-27 起另一项任务留下的，[36](36-day-agenda.md) 当时已经提到过它编译不过。

### P0-3 信息过载：规则条款直接上了屏

本次截图里能直接看到：

- **夜战面板**除了三面的操作行，还有 6 行说明文字，其中两行是设计条款原文，例如"施工遭尸潮、夜袭、战斗、天亮或身死中断时退回材料，已耗精力不退"。玩家在 40 分钟的轮间要做决定，却得先读完这些。
- **选身份页**（第一屏选择）就写着"身份解法：可选「校勘七灯旧文」；旧世确证后可选……两法均须今世取证"。新玩家还不知道什么是七灯、旧世、取证。
- **外出页**左栏的描述和主线状态被截断（"仓里兴许还剩些…"、"青云尚待…"）。
- **劫余录**有 9 个子入口（本世开局 / 尸劫来历 / 身份与旧世 / 轮回调查 / 前世记忆 / 邻里事务 / 纸鹤往来 / 邻人与商情 / 风声与危机），而一局只有 20 天、约 2 小时。
- 开局前要过 4 屏（标题 → 身份 → 难度 → 立愿：誓约、凭仗、了愿、两种模式、同院、开局筹备），然后才是三天备劫。

[33](33-goal-brief.md) 自己的诊断也是"信息都在，但没有人替玩家把它们合成一句话"。`brief.gd` 做了归纳，但入口和条款原文都还在。

### P1-4 动态世情不随包发布

便携包说明里写的是"本包不包含所需的本地服务"。也就是说，世情导演、NPC 受控对话、轮回调查的 AI 排期，只有开发机上能跑；任何试玩者拿到的都是离线固定内容。这部分投入对玩家目前是不可见的。

### P1-5 平衡数据过期

四档难度的劫满率来自 v0.8，每档 6 局，在差事单、主线减潮、针对布防、东侧院和地窖之前。[36](36-day-agenda.md) 已经测到：带差事单、一天跑两趟的机器人 24/24 劫满，收局余柴 25 捆、气血满。默认档可能已经偏松，但没人重测过。

### P1-6 夜战这个高潮仍以面板为主

一夜三轮里只有第 1 轮有 3D 演出，第 2、3 轮是面板加战报（开门迎敌除外）。开门迎敌时，同一句"有东西挤进院子了！"会叠成 4 条提示；夜里左侧 HUD 仍然显示邻里、主线、轮回旧案这些和战斗无关的面板。

### P2-7 发行基础薄

- 没有正式 exe（导出模板没装上），便携包约 372 MB；
- 字体靠系统楷体回退，没装楷体的机器上外观不可控；
- 美术混搭：存货里米袋是写实贴图，其余是代码画的简笔图标；写实家具、低模铺面、代码构件同屏；
- 只有两首配乐，夜里没有专门的曲子。

### P2-8 工程债

- 三个 1500–2200 行的大文件，改任何弹窗都要动 `dialogs.gd`；
- 没有 CI，也没有统一的测试入口，106 个场景测试要一个个跑；
- 测试在玩家数据目录 `%APPDATA%\Godot\app_userdata\劫余录\` 根下留了 68 个残留文件（`mainline-ui-*.json`、`*_shot.png` 等）；
- 每次退出都有 RID / ObjectDB 泄漏警告。

### P2-9 过程成本高于产出

10-28 这一天 20 次提交：上午 6 次宅院营造功能，当天就全部合入；15:22 以后的 11 次里，有 10 次是存档、打包、试玩包的边界加固（回溯失败、合卷失败、续写、写探针……）。这些都是审查中发现的，没有一条来自玩家报告。[10](10-roadmap.md) 有 177 行，大半是"上一批"流水。按"进展只看用户能用的功能有没有变化"的标准，这些投入的边际收益已经很低。

## 3. 路线图

四个阶段，前两个是硬顺序，C 可以和 B 后半并行，D 只在试玩证实核心循环成立后才开。

### 阶段 A：试玩闭环（约 1 周，功能冻结）

| # | 做什么 | 验收 |
|---|---|---|
| A1 | 处理工作区里的结局复盘：修掉变量重名后按功能提交，或者先收起来 | `check_scripts` 0 失败；`--demo=ending` 能出图 |
| A2 | **快速开局**：标题「开始」直接用默认身份、寻常年景、不立愿、普通开局进备劫，高级选项折叠起来；第一世的身份卡只写身份和特长，"身份解法 / 旧世经验"从第二世才显示 | 从标题到能操控角色 ≤ 3 次点击；第一世选身份页不出现"取证""旧世"这类词 |
| A3 | 从干净提交出试玩包（已有 `build_windows_clean.ps1`），并明确按**离线**体验测试——这才是玩家实际会拿到的 | 包能启动，读我写清离线 |
| A4 | 3–5 人试玩，照 [30](30-playtest.md) 的问法；作者自己也盲玩一整局 | 至少收回 3 份 `report.md`；记下首次死亡日、能否说出死因、第 10 日卡在哪、一局实际多长、在哪里放弃 |
| A5 | 把试玩结论写成一张问题表，用它给阶段 B 重新排序 | B 里每一条都标上"试玩证实 / 未证实 / 被否定" |

**冻结**的意思是：这一周不加新系统、不加新的存档加固，只修试玩暴露的阻断问题。

### 阶段 B：收拢核心体验（2–3 周，顺序由 A5 决定）

下面每一条都是**假设**，A4 的试玩没有证实就不做。

| # | 做什么 | 验收 |
|---|---|---|
| B1 | **规则文本减负**：面板正文只说"会发生什么、要花什么"，条款类说明挪进悬浮提示和玩法说明 | 夜战面板正文 ≤ 3 行；外出左栏不截断；1280×720 截图目视 |
| B2 | **劫余录收拢**：9 个入口并成 3 页（今世：目标、主线、危机；人：邻里、纸鹤、邻人；前世：开局、身份、轮回、记忆）；还没触发的系统不显示入口 | 第 1 日打开劫余录可见入口 ≤ 3 个；现有窗口测试改造后仍通过 |
| B3 | **夜战观感**：同类提示 N 秒内合并成一条（"×4"）；第 2、3 轮至少把镜头切到破面，或补轻量 3D 演出；夜里收起和战斗无关的 HUD 面板 | 开门迎敌时同句提示最多 1 条；夜里左侧只剩预兆和守面 |
| B4 | **平衡重测**：sim 机器人接上差事单，每档 24 局。建议的机器人劫满率目标：暖冬 ≥ 90%、寻常 60–75%、荒年 35–50%、永夜 15–30%（真人应低于机器人）。超出区间就调 `difficulty.json` 或差事产出 | 四档都落在区间内，且没有倒挂 |
| B5 | **白天节奏复核**：如果试玩者把差事单当成"清单式苦工"，就把 29 条差事并成少量有取舍的时段块（上午 / 下午 / 傍晚） | 由试玩回答，机器人不能验收 |

### 阶段 C：可发行基础（2–4 周，可与 B 后半并行）

| # | 做什么 | 验收 |
|---|---|---|
| C1 | **动态世情怎么发——需要你拍板**。(a) 离线优先：把已回放验证的 AI 事件固化成手写事件池，事件从 23 条扩到 60 条以上，导演保留为可选；(b) 托管代理：要服务端、费用、隐私和密钥治理。**建议 (a)**：成本低，而且试玩包现在本来就是离线的 | 选定方案；(a) 的话事件密度从 0.3–0.8 次/天提到 ≥ 1 次/天 |
| C2 | 正式 exe：装上导出模板（换镜像或一次性下载），做体积治理和图标 | 产出独立 exe；体积有记录 |
| C3 | 内置开源中文字体（如霞鹜文楷，OFL 许可），去掉系统楷体依赖 | 在没装楷体的机器或虚拟机上截图一致 |
| C4 | 美术统一，先做花钱最少的：统一存货图标风格（米袋写实图换掉，或全换成手绘），补夜间配乐；人物体型和代码拼的铺面放后面 | 存货页一屏内风格一致 |
| C5 | CI 与统一测试入口：`tools/run_tests.ps1 -Tier fast|core|ui|full`；GitHub Actions 只跑 `check_scripts` 和无界面规则测试 | 推送后 CI 自动给出结果 |

### 阶段 D：深度内容（试玩证实核心循环成立以后）

按 [07](07-survival-log-features.md) 第 11 节的缺口挑，每一项都要先回答"会不会再加重 P0-3 的认知负担"：

- 收集：图鉴、成就——成本低，复玩价值高，优先；
- 外出：地点独有目标、哄抢；
- 经营：保质期与霉变、自由烹饪——会加日常压力，也会加操作量，要和 B5 的结论一起定；
- 宅院营造 C7 及以后：暂停。

### 并行：工程债（每周最多一批，不挤占 A、B）

1. 按系统把 `dialogs.gd` 拆成 `scripts/ui/dialogs/*.gd`，`post_screen.gd` 的 HUD 拆成组件；
2. 测试残留不再落到玩家数据目录根下：统一用一个临时子目录，跑完清掉；
3. 查掉退出时的 RID / ObjectDB 泄漏警告；
4. [10](10-roadmap.md) 只保留往后看的部分，批次流水挪到 CHANGELOG。

## 4. 暂停清单

- 没有玩家报告的存档、打包边界加固；
- 新的跨轮回机制——等有人真的玩完两世再说；
- 宅院营造的新批次；
- A、B 以外的任何新系统。

## 5. 度量：只看玩家感知得到的

| 指标 | 目标 | 怎么量 |
|---|---|---|
| 上手 | 标题到能操控角色 ≤ 60 秒 | 试玩录屏或计时 |
| 理解死因 | 试玩者能说出自己怎么死的 ≥ 4/5 | [30](30-playtest.md) 的问题 2 |
| 卡点 | 第 10 日"想做做不了"的事有记录，且每条都有归属 | 问题 3 加报告 |
| 一局时长 | 有实测分布，而不是估算 | 报告里的天数和时间戳 |
| 难度 | 机器人劫满率在 B4 的区间内，真人低于机器人 | sim 加报告 |

## 6. 对抗式审查：这份路线图可能错在哪

| 质疑 | 回应 |
|---|---|
| "冻结一周会拖慢进度" | 现在每加一个功能都是在没有反馈的情况下押注。一周试玩的成本，低于在错误方向上再叠两周系统 |
| "找不到试玩者" | 底线是作者本人盲玩一整局并导出报告；再请 2–3 个朋友。样本小也比零好 |
| "动态世情是卖点，不该降级" | 玩家拿不到的卖点不是卖点。方案 (a) 不删导演，只是把它的产出固化下来；以后要做托管，事件池和规则校验都还能用 |
| "收拢会抹掉深度" | 用的是渐进解锁，不是删除：第一世只露核心，后面的系统在触发时才出现 |
| "B4 的目标区间是拍脑袋定的" | 是起点，不是结论。真人数据回来后按真人和机器人的差距再校 |
| "P0-3 只是作者的感觉" | 证据来自截图和入口计数；但"玩家是否因此卡住"仍要 A4 回答，所以 B1、B2 被标成假设 |

## 7. 本次分析的依据与未验证项

- **实际运行**：用 `--demo` 在 1280×720 拍了 10 个场景（title / roles / pre / post / night_panel / gate_fight / explore / inventory / dead / ending），9 张成功；ending 因 P0-2 解析失败没有出图。
- **读过**：README、文档 04 / 07 / 08 / 10 / 27 / 30 / 33 / 34 / 35 / 36、`post.gd` 的常量与行动表、`dialogs.gd` 的入口列表、打包脚本、`data/*.json` 的条目数、git 历史，以及本机 `user://` 目录的文件清单。
- **NOT RUN**：任何自动化测试、真人试玩、打包；没有逐行审查各系统的规则正确性。
