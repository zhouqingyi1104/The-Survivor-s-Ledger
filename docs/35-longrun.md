# 长局稳定性

2026-10-27。「守到死」模式没有终点，谁也不知道玩家能撑到第几日。这批要回答一个问题：**活得越久，游戏会不会越来越慢或状态越来越大？**

## 怎么量的

不用机器人真跑两千天（它活不到），而是**构造**极端局面：把 `run.pday` 直接推到第 20 / 480 / 1000 / 2000 日，日志写满、快照塞满，再测三件事：

1. 存档体积（`JSON.stringify` 后的字节数）
2. `Post.advance(run, 1440)` 过一次"一天"的 CPU 时间
3. 核心小工具（目标要务、死因账本、试玩报告）在这个日数下还能不能算

## 实测

| 日 | 存档 | stringify | 过一天 |
|---|---|---|---|
| 20 | 87 KB | 1.7 ms | 9.8 ms |
| 480 | 89 KB | 2.0 ms | 111 ms |
| 1000 | 91 KB | 1.9 ms | 212 ms |
| 2000 | 91 KB | 1.7 ms | 421 ms |

三个结论：

- **体积不膨胀**：87 → 91 KB。因为日志在 `State.LOG_LIMIT = 300` 条封顶、快照在 `Ledger.SNAPSHOT_KEEP` 份封顶，两个都是既有设计——这批只是把它们钉成断言。
- **序列化成本稳定**：1.7–2.0 ms，与日数无关。存档每次行动都写一遍，这条最要紧。
- **CPU 随日数线性增长**：约 0.2 ms/天（一天的成本）。来源是 `Post.trade_refresh` 里的世界时钟刷新（危机、主线、身份、轮回调查、纸箱往来、邻人自主行动），每次 tick 都会跑一遍，而其中若干处会随 `pday` 变大而多做事。

### 线性增长要不要修

**不修，但它有记录在案的理由**：

- 真实场景里玩家能活到的天数是 30–40 日（无尽模式实测：劫满后平均多守 4.5 日），此时过一天约 15 ms。
- 摊到每个 tick 上：第 2000 日时单 tick 约 2.9 ms，而 3x 流速下一个 tick 要跨约 25 帧才发生一次——占不到帧预算的千分之几。
- 真要治，得拆开 `trade_refresh` 里那七个 `poll`（每个都有独立的时钟状态），属于"改结构"而不是"改数值"，风险远大于收益。

## 交付：`tests/longrun.gd`

20 项断言，三类：

| 类别 | 断言 |
|---|---|
| 体积 | 第 20 日与第 2000 日均 < 200 KB；两者差值 < 20 KB（再多就是有东西没封顶） |
| 封顶 | 连写 5000 条日志后仍 ≤ `LOG_LIMIT` 且保留的是最新的；塞 150 天快照后 ≤ `SNAPSHOT_KEEP` 且保留最新的 |
| 不崩 | 第 2000 日过一天 < 5 秒、返回结果是已知的那几种、`phase` 仍然是 post/dead/ending、气血在 [0, 上限] 内、日子不倒流；目标要务 / 死因账本 / 试玩报告在 2000 日都还能出 |

**时间断言一律留大余量**（5 秒而不是 500 毫秒）：机器差异比代码退化更容易让测试假红。真正钉死的是**体积**和**不崩**——这两条与机器无关。

## 未做范围

- **没有跑真正的长局**：这批是构造出来的极端局面，不是"机器人真的守了两千天"。机器人活不到那天，用构造法测的是"如果活到了会怎样"。
- **没有修那 0.2 ms/天**：理由是上面那段，属于设计取舍不是遗漏。
- **没测渲染与 UI**：只看 core 的 CPU 与体积。第 2000 日时劫余录面板、日志滚动、快照列表的界面表现没验。
- **没测内存峰值**：`duplicate(true)` 的深拷贝（快照、报告）在大状态下的峰值占用没量。
- 存档体积上限 200 KB 是**经验值**（现在 91 KB 的两倍），不是从磁盘/网络约束推出来的。
