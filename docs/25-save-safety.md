# 存档安全与可恢复

2026-10-26。承接路线图 M5「可发布版本」的**存档**一项。验收以「玩家一局不会因为一次断电、磁盘写满或进程被杀而整局消失」为准，改前改后的读档语义逐项对账。

## 问题（第一性原理）

存档这件事只有一个硬指标：**写进去的东西，下次一定能读回来**。它同时要抵抗三类现实故障：

1. **写一半被打断**（进程被杀、断电、磁盘写满）——留下半截 JSON；
2. **读完才发现是坏的**——玩家点「续写此录」才知道这一局没了；
3. **再写一次就彻底没救**——坏档被下一次写入覆盖，连残骸都不剩。

改前这三点全不设防：

- `Game.save_game()` 直接 `FileAccess.open(save_path, WRITE)` 覆盖主档。写的中途断掉，好档当场变半截。
- `continue_game()` 读不出来只 `toast("存档读不出来。")` 就 `return`，没有第二份可退、没有说明、没有留档。
- `_ready()` 读 `meta.json`（跨轮回的道心底稿）失败时**静默** `State.new_meta()`，玩家攒的道心、残卷、永久经验不声不响归零。
- `save_meta()` 写失败只 `return`，控制台一行错都没有，玩家以为存上了。
- `_delete_save()` 只删主档——一旦有了备份，会变成「合上旧卷后旧局从备份里活过来」。

**验收条件**：① 主档任何形式的损坏都不会让玩家失去可玩的一局；② 退备份时必须让玩家知道退了一步，不许静默；③ 两份都坏时不冒充成功、不删原文件；④ 写入失败要出声；⑤ 合上旧卷／开新卷后备份不能把旧局救回来；⑥ 每次行动后的写盘开销不能比改前明显变慢。

## 方案

新增 `scripts/core/save_file.gd`（纯逻辑、可无界面测试），`Game` 只做一层转发。

### 写：三步，任一步失败都不动现有主档

| 顺序 | 动作 | 失败后的结果 |
|---|---|---|
| 1 | 新内容写入 `path.tmp` | 主档原样，报 `write` |
| 2 | 回读 `path.tmp` 与待写文本**逐字比对** | 主档原样，删 tmp，报 `verify` |
| 3 | `path` → `path.bak` 改名轮换 | 主档原样，删 tmp，报 `backup` |
| 4 | `path.tmp` → `path` 替换 | 把 bak 挪回 main，报 `replace` |

真正的「替换」只有第 4 步一次改名，所以主档在任何瞬间都只可能是**上一版完整内容**或**这一版完整内容**，不会是半截。

### 读：主档坏了退备份，并且说清楚

`read()` 返回 `{"data", "source", "note"}`：

| 情形 | source | note | 玩家看到 |
|---|---|---|---|
| 主档可用 | `main` | `main_ok` | 正常续写 |
| 主档坏、备份可用 | `backup` | `main_bad` | 标题「续写此录 · 从备份」；读档后提示退了一步 |
| 主档没了、备份可用 | `backup` | `main_missing` | 同上 |
| 两份都坏 | `""` | `main_bad` | 标题「续写此录 · 读不出」；点进去明确说读不出，原文件不删 |

`meta.json` 走同一条路：退了备份就提示；两份都坏才重起账，并把读不出的那份**改名留底**成 `meta.json.bad`，不直接覆盖。

### 备份的语义（写明，免得以后误读）

`.bak` 是**上一次成功写进去的完整内容**，不是「历史上最好的一份」。主档当时已经坏了也会被轮换进 `.bak`，但下一次写入就把它换成好的，不会越滚越坏——因为写入已经是原子的，主档只会是完整版本，坏了只可能来自旧版本或外部改动。

## 实测与取舍（一次性探针，用完即删）

探针 `tests/_probe_rename.gd`、`tests/_probe_cost.gd`，跑完删除，不进库。

- **`DirAccess.rename_absolute` 在 Windows 上覆盖已存在目标是成功的**（返回 `OK`，目标变成源的内容，源消失）。这是「改名轮换」和「最后替换」两步的前提。
- 一局玩到第 20 日、带 20 页生死簿快照，实测存档约 **600 KB**，分步耗时：

| 步骤 | 耗时 |
|---|---|
| `JSON.stringify`（改前就在付） | 14.8 ms |
| 写一份 600KB | 1.8 ms |
| 回读 + 逐字比对 | 1.7 ms |
| 解析整份 JSON | 10.1 ms |
| 改名 | 1.1 ms |

由此定下两个取舍：

1. **校验用「回读逐字比对」而不是「解析整份 JSON」**：1.7 ms vs 10.1 ms，而且抓的是同一类故障（截断、写一半、编码坏），逐字比对甚至更严——解析成功但内容被改这种事它也能发现。
2. **备份用「改名轮换」而不是「复制一遍」**：省掉一次 600 KB 的满写。原本的写法是读旧主档 + 写 bak，实测多花约 1.8 ms 和一次读，不值当。

改后每次行动多付约 **4 ms**（写 tmp 1.8 + 回读比对 1.7 + 两次改名 2.2，实测合并后约 4–5 ms），相对改前已经存在的 14.8 ms `stringify` 可以接受。

## 未做范围

- **多存档槽、手动存档/读档、存档导出导入**（玩家把档发给别人）——本期只保证单槽不丢。
- **真正落盘的 `fsync`**：写盘后未强制刷盘，操作系统崩溃仍可能丢最后一次；进程被杀这一档已经覆盖。
- **Steam 云 / 跨设备同步**。
- **存档体积治理**：20 页快照各自是一整份局势，后期存档 600 KB 且每次行动全量重写。要不要改成增量或压缩，等节奏和发布方案一起定。
- 旧存档（v20 以前）**没有** `.bak`，第一次写入后才有；这一批不回溯补造备份。
